# Effect v4 on Cloudflare Workers

Research for issue #4 (part of the map, issue #3). Effect v4 is a BETA/RC. Every claim below is sourced from v4 docs, the `Effect-TS/effect` repo (which now hosts v4 development on `main`, with v3 moved to a `v3` branch), or npm dist-tags fetched during this research. No claim is from memory or from Effect v3 documentation. Where v3 and v4 differ, or where a fact could only be confirmed against v3-era sources, that is called out explicitly.

## Summary

1. Effect v4 has no dedicated Cloudflare Workers platform package; it ships generic web-standard `Request`/`Response` handlers (`HttpApiBuilder.toWebHandler`, `HttpEffect.toWebHandler`) that run on workerd, same pattern used for Deno/Bun/browser.
2. `effect@rc` (currently `4.0.0-rc.112`) and `effect@beta` (`4.0.0-beta.107`) are both live npm dist-tags; `effect@latest` is still v3.22.1 — v4 is not GA.
3. HttpApi, Schema, Rpc, Cluster, Workflow, CLI, AI and SQL modules all moved inside the core `effect` package under `effect/unstable/*`; most companion packages (`@effect/platform-*`, `@effect/sql-*`) are versioned in lockstep and also carry `beta`/`rc` tags.
4. `HttpApi` declares endpoints once and drives four things from that single definition: server routing (`HttpApiBuilder`), a typed client (`HttpApiClient`), URL builders, and an OpenAPI 3.1 spec (`OpenApi.fromApi`) — no separate codegen step, and v4 adds an `HttpApi.gen` module that can also generate schemas/clients from an existing OpenAPI spec.
5. Schema v4 is a full rewrite ("Schema v4... a complete redesign... for explicitness, composability, and tree-shaking") and ships a `Schema.standardSchemaV1`-style export so an Effect schema can be handed to any Standard Schema consumer.
6. There is no first-party Effect layer over Durable Object bindings, D1, R2 as Worker-binding services; `@effect/sql-d1` exists (versioned with v4 tags) for D1, but `@effect/sql-sqlite-do` (Durable Object SQLite) has two **open** bugs where `SqlClient.withTransaction` emits `BEGIN`/`COMMIT`, which workerd's Durable Object SQLite storage rejects outright.
7. A separate **open** bug (effect-ts/effect#6319, filed against 3.21.2 but describing the exact `HttpApp.toWebHandlerLayerWith` code path still used by the httpapi/rpc web-handler builders) shows a client-aborted first request into a cold isolate can permanently wedge a Worker (Cloudflare error 1101) because the memoised layer-build promise never settles.
8. No official Effect testing guidance for Cloudflare's `@cloudflare/vitest-pool-workers` was found; `@effect/vitest` (Layer sharing, `it.layer`, `TestClock`) is documented only against Node/Bun/browser-style test runners.
9. Bindings: nothing in v4's docs or source changes the repo's own rule — `import { env } from "cloudflare:workers"` at module scope is Cloudflare's current API and is independent of Effect; Effect's own examples for Workers (community `effect-cf`, and the `HttpApiBuilder.toWebHandler` pattern) construct their `Layer`s at module scope too, so the two compose without per-request env threading.
10. For a maintainer new to Effect: the smallest idiomatic server is small (one `HttpApi.make` + one `HttpApiBuilder.group` + `HttpApiBuilder.toWebHandler`), but v4's beta status, thin Workers-specific documentation, and the two open Durable-Object/cold-start bugs above are real costs, not just a learning curve.

## Does Effect v4 run on workerd today, and what does a Worker entry look like? Known gaps.

**Runs on workerd:** yes, but only in the generic sense that Effect v4 targets any environment with `fetch`, `Request`, `Response`, and standard web APIs; there is no Cloudflare-specific platform package analogous to `@effect/platform-node` or the new `@effect/platform-deno`. `npm view @effect/platform-deno dist-tags` returns `beta`/`rc` tags (confirmed live during this research), but there is no `@effect/platform-cloudflare-workers` or `@effect/platform-workerd` package on npm under any dist-tag — checked via `npm view @effect/platform dist-tags`, which returned no `beta`/`rc` at all (only `latest: 0.97.1`, a v3 release), meaning `@effect/platform` itself has not been re-published under the v4 line; the platform functionality lives inside `effect/unstable/http` and `effect/unstable/httpapi` in the core `effect` package instead. Source: `effect-ts/effect` `packages/effect/README.md` (fetched via GitHub) states "functionality that previously lived in separate packages ships inside `effect` under the `effect/unstable/*` namespaces, including `http`, `httpapi`, `rpc`, `cluster`, `workflow`, `cli`, `ai`, `sql`, and `reactivity`."

**A Worker entry:** the shape confirmed across multiple v4/near-v4 sources is:
```ts
export default {
  fetch: HttpEffect.toWebHandler(handler), // or HttpApiBuilder.toWebHandler(ApiLive).handler
}
```
— quoted from an open feature request against `effect-ts/effect-smol` (issue #1492, "`HttpApiBuilder` add a way to make standalone handler that doesn't [need the router]"), which uses `effect/unstable/httpapi` imports, confirming this is v4-shaped code, not v3. `HttpApiBuilder.toWebHandler` returns `{ dispose, handler }` where `handler: (request: Request, context?) => Promise<Response>` — a plain web-standard fetch handler, which is exactly the shape `export default { fetch }` requires on Workers.

**Known gaps found in the official issue tracker** (all in `effect-ts/effect`, all open at time of research):
- **#6319** — "`HttpApp.toWebHandlerLayerWith` memoises the layer build inside the first request — an aborted first request permanently hangs the isolate on Cloudflare workerd (error 1101)." Filed against `effect@3.21.2`/`@effect/platform@0.96.1`, but the code path it describes (`handlerPromise ??= Effect.gen(...).pipe(Scope.extend(scope), Effect.runPromise)`) is the same memoization strategy `HttpApiBuilder.toWebHandler` and `RpcServer.toWebHandler` use; this repo could not confirm from the tracker whether v4's `effect/unstable/http`/`httpapi` rewrite has already fixed it — flagged as an open risk, not a confirmed v4 bug. workerd cancels a request's IoContext on client disconnect, and a promise created inside that cancelled context "never settles," per the issue body, which cites Cloudflare's own behavior.
- **#6169** — `RpcSerialization.msgPack` silently fails on Cloudflare Workers because msgpackr's JIT-record-optimization path calls `new Function()` at *decode* time; Cloudflare's `allow_eval_during_startup` compat flag permits `new Function()` only during module init, so msgpackr's own startup probe gives a false pass and then throws on a real request. Filed against `@effect/rpc` 0.75.0 — relevant if the RPC transport (not HttpApi) with msgpack serialization is chosen; JSON serialization is unaffected.
- No `nodejs_compat` requirement was found documented anywhere in Effect's own docs for the httpapi/schema/http path — Effect's HTTP/Schema code is written against web-standard APIs (`Request`, `Response`, `fetch`), so `nodejs_compat` should not be required for the core library. This is an inference from the module design (`effect/unstable/http` targets `Request`/`Response`), not a directly cited "no nodejs_compat needed" statement from Cloudflare or Effect — **not found** as an explicit claim in either source set.
- **Bundle size**: InfoQ's coverage of the beta launch (linked from effect.website's own blog search results) states "a minimal program using Effect, Stream, and Schema drops from roughly 70 kB in v3 to about 20 kB in v4" — this is a secondary source (InfoQ), included because effect.website's own blog post series ("This Week in Effect") repeatedly references the same bundle-size rewrite as a headline v4 goal; no first-party effect.website page with an exact number was fetched successfully in this pass, so treat the 70kB→20kB figure as reported-by-InfoQ, not effect.website-primary.
- **Cold start**: not found in v4 sources. No effect.website or GitHub source measuring Worker cold-start time with Effect v4 was located.

## HTTP layer: API declaration, typed clients, OpenAPI, error transport

Source: `effect.website/docs/v4/api/effect/unstable/httpapi/HttpApiClient` and `.../OpenApi` (fetched directly), plus the `effect-smol` issue #1492 quoted above for `HttpApiBuilder`/`HttpApiGroup`/`HttpApiEndpoint`/`HttpApi` construction.

- **Declaring an API**: `HttpApiEndpoint.get("name", "/path", { success: SomeSchema })`, grouped with `HttpApiGroup.make("groupName").add(endpoint)`, assembled with `HttpApi.make("apiName").add(group)`. Implementations are wired with `HttpApiBuilder.group(Api, "groupName", (handlers) => handlers.handle("name", (ctx) => ...))`.
- **Typed client**: `HttpApiClient` module — `HttpApiClient.make` "constructs a type-safe client for an HTTP API using the `HttpClient` service, endpoint schemas, middleware, and optional client or response transformations"; `HttpApiClient.makeWith` takes a supplied `HttpClient` directly. Because the client is built on Effect's `HttpClient` service (an abstraction over `fetch`), and v4 already ships `@effect/platform-browser` and a new `@effect/platform-deno` (both carrying `beta`/`rc` npm tags, confirmed live), the client is fetch-based and portable to any JS runtime, including React Native's global `fetch` — but **no source found explicitly names React Native** as a tested/supported target; this is an inference from "fetch-based client," not a directly cited claim, so treat React Native support as **not found in v4 sources**, only inferred from the transport being `fetch`.
- **OpenAPI**: `effect/unstable/httpapi/OpenApi` module, function `OpenApi.fromApi`, "Generates an OpenAPI 3.1 specification from an `HttpApi`" — confirmed by direct fetch of the v4 API reference page. v4 additionally adds an `HttpApi.gen` code-generation module (per the "Effect v4 Beta: July 2026 Updates" blog recap) that can generate Effect Schema types, HTTP clients, and HttpApi modules *from* an OpenAPI spec — the reverse direction, useful for consuming third-party APIs, not needed for `apps/server`'s own contract.
- **Typed errors over the wire**: HttpApi endpoints declare error schemas per-endpoint (the same `HttpApiEndpoint` builder accepts an `error` schema alongside `success`), and the same schema definition drives both the server's error encoding and the generated client's error decoding — the July 2026 recap explicitly lists "fixed client error and authorization decoding" as recent hardening work on this exact path, confirming errors are schema-encoded and decoded on the client, not just thrown as opaque HTTP status codes.

## Effect Schema in v4: the schema library, and Standard Schema

Source: `effect.website/docs/v4/schema/introduction` (fetched directly).

- Schema v4 is described as "a complete redesign of the Schema module... with a focus on explicitness, composability, and tree-shaking," with v4 schemas tracking 14 type parameters (v3 tracked 6–8) to "preserve complete type information through composition."
- It lives inside `effect/unstable/schema` per the same package README cited above, i.e., it ships inside the core `effect` package in v4, not a separate `@effect/schema` package — so "is it the schema library now" is confirmed yes, by virtue of being folded into core rather than being an optional add-on.
- **Standard Schema**: the introduction page's operations table includes "Standard Schema: Generate a Standard Schema V1," and effect.website documents a dedicated page at `/docs/v4/schema/standard-schema` — confirming Effect Schema v4 does implement/expose Standard Schema V1, so other Standard-Schema-aware tooling (form libraries, validators) can consume an Effect schema directly. The exact function name (`Schema.standardSchemaV1` per a third-party migration-guide mirror) was not independently re-confirmed on effect.website itself in this pass — flagged as sourced from a secondary mirror (`effect-ts-effect-smol.mintlify.app/migration/schema`) for the exact identifier, while the *capability* itself is confirmed primary via effect.website.

## Services and layers onto Worker bindings (D1, R2, Durable Objects, secrets) per request

This repo's own binding rule (`docs/agents/cloudflare.md`) already establishes: read `env` once at module scope via `import { env } from "cloudflare:workers"`, build module-level singletons (e.g. `drizzle(env.DB, { schema })`), never thread `env` per request. Nothing found in Effect v4 sources contradicts or requires deviating from that — Effect's own Layer model is *designed* for exactly this: a `Layer` is typically constructed once (module scope) and provided to the runtime, matching "no per-request env threading."

- **D1**: `@effect/sql-d1` exists as a package and carries the same `beta`/`rc` npm dist-tags as core `effect` (`4.0.0-beta.107` / `4.0.0-rc.112`, confirmed via `npm view @effect/sql-d1 dist-tags`), so it is being versioned in lockstep with v4. A D1 `Layer` would be built from `env.DB` at module scope, same as the repo's Drizzle pattern, then provided into the Effect runtime.
- **R2**: no dedicated `@effect/sql-r2` or `@effect/storage-r2` package was found on npm; R2's binding (`env.R2_BUCKET`) is a plain Cloudflare `R2Bucket` object, so an Effect service wrapping it would be hand-written (`Context.Tag` + a `Layer.succeed`/`Layer.effect` built from `env.R2_BUCKET`) — **not found**: no official Effect R2 integration exists.
- **Durable Objects**: no official Effect package for DO namespace bindings either. The community package `effect-cf` (third-party, not Anthropic/Cloudflare/Effect-official) advertises "Storage services for R2, KV, D1, Queues, and Workflows" and Durable Object support with alarm transactions — flagged explicitly as third-party, unofficial.
- **Secrets/vars**: no Effect-specific handling needed beyond the same module-scope `env` read; Effect's `Config` module can wrap `env` values into `Config.succeed(...)`-style layers if typed config access is wanted, but this is generic Effect usage, not Workers-specific.
- **The one binding that is legitimately per-request, not module-scope**: `ExecutionContext` (`ctx.waitUntil`, `ctx.passThroughOnException`), because it is created fresh by the runtime for each incoming request/event and cannot be captured at module load — Cloudflare's own Workers docs describe `ExecutionContext` as passed into each `fetch`/`scheduled` handler invocation, not sourced from `cloudflare:workers`'s module-scope `env` export. No Effect-specific pattern for `ExecutionContext` was found in v4 sources; it would need to be passed into the request-scoped Effect run (e.g. via `Effect.runPromise` invocation arguments or `HttpApiBuilder.toWebHandler`'s optional `context` parameter), which is the one place a per-request value legitimately has to flow in.

## Durable Objects from Effect: can fetch/WebSocket handlers run an Effect runtime cleanly

- **Two open bugs directly contradict "cleanly" for the SQL-transaction case**: `effect-ts/effect#5987` and `#6006` (near-duplicate reports) both show `@effect/sql-sqlite-do`'s `SqlClient.withTransaction` issuing `BEGIN`/`COMMIT`/`ROLLBACK` against Durable Object SQLite storage, which workerd rejects — Cloudflare's own docs are quoted in the issue: "`sql.exec()` cannot execute transaction-related statements like `BEGIN TRANSACTION` or `SAVEPOINT`." Cloudflare DO SQLite instead auto-coalesces synchronous writes into an implicit transaction, so the fix (per the issue's own "expected behavior") would be `sql.withTransaction` becoming a no-op or using `state.storage.transactionSync`, not `BEGIN`/`COMMIT`. **Both issues are open** as of this research (last updated 2026-07-14) — this is a real, currently-unresolved gap for any DO-with-SQLite-storage Effect service (which is exactly the map's "per-workspace Durable Object with its SQLite storage" fallback path).
- The cold-start/wedge bug (#6319, above) also applies to DO fetch handlers if they're built with the same `toWebHandlerLayerWith`-style memoization, though the issue itself was filed against a plain Worker, not a DO.
- No source (official or community) was found demonstrating a WebSocket handler (`webSocketMessage`/`webSocketClose` DO methods) driven by an Effect runtime — **not found in v4 sources**.
- The community `effect-cf` package claims full DO support including alarms with "transactional guarantees," which — if accurate — would route around the `withTransaction` bug above by using its own DO-aware primitives rather than `@effect/sql-sqlite-do`'s generic SQL client. This is a third-party claim, not verified against its source in this pass beyond the README.

## Testing: swapping services, and Cloudflare's Vitest pool

- **Swapping services in tests**: `@effect/vitest` is the documented mechanism — `it.effect` runs a scoped test with Effect's built-in test services (`TestClock`, `TestConsole`); `it.layer` "shares a Layer between multiple tests," which is the idiomatic way to substitute a mock/test `Layer` (e.g. a fake D1/R2 service) for the production one. Source: GitHub `effect-ts/effect` `packages/vitest/README.md` and the `@effect/vitest` npm page, both surfaced via search; not independently re-fetched line-by-line in this pass, so treat the exact API names as reported rather than directly quoted from the primary README text.
- **Inside Cloudflare's Vitest pool (`@cloudflare/vitest-pool-workers`)**: **not found** — no source, official or community, documents `@effect/vitest` running inside `@cloudflare/vitest-pool-workers`. Cloudflare's own pool runs the Vitest runner *inside* workerd via a bundled `vitest/worker` module and has had recent breaking changes (v0.13.0 replaced `defineWorkersProject`/`defineWorkersConfig` with a `cloudflareTest()` Vite plugin, per `cloudflare/workers-sdk` issue tracking surfaced in search) and version-compatibility issues with newer Vitest majors (`cloudflare/workers-sdk#13581`, `#11064`). Given `@effect/vitest`'s own `it.effect`/`it.layer` helpers are themselves a Vitest wrapper, compatibility would depend on whether both wrapper layers agree on the same Vitest runtime internals — no source confirms or denies this combination has been tried. This is the least-covered area of the whole research and should be treated as an open risk requiring a hands-on spike, not a documented fact either way.

## Learning curve for one maintainer new to Effect (coming from Rust)

- The smallest idiomatic server shape confirmed across sources is: one `HttpApi.make(...)` + `.add(HttpApiGroup...)` schema declaration, one `HttpApiBuilder.group(...)` implementation `Layer`, and one `HttpApiBuilder.toWebHandler(ApiLive).handler` exported as the Worker's `fetch`. This is a small, declarative surface, and Effect's `Layer`/service model maps reasonably well onto Rust intuitions (traits ~ `Context.Tag`, trait impls ~ `Layer`s, `Result`/typed errors ~ Effect's typed error channel) — this comparison is this report's own inference for the reader, not a claim sourced from Effect's docs.
- Real costs specific to *v4 today*, not just "Effect is a learning curve": (1) it is a beta/RC, so APIs are still moving between beta.N releases (npm shows beta.82 through beta.107 then rc.108–112 in the version history pulled during this research — frequent point releases); (2) Workers-specific documentation is thin to nonexistent on effect.website itself — every Workers-specific fact in this report came from GitHub issues or third-party blog/community sources, not effect.website's own docs tree, meaning a maintainer new to Effect has no first-party "Effect on Cloudflare Workers" guide to follow; (3) the two open Durable-Object-SQLite-transaction bugs and the cold-start-wedge bug are exactly the kind of runtime-specific landmine a newcomer would not know to look for.

## Scorecard against the map's transport ranking

Ranking, in order, from issue #3's Notes: (1) end-to-end types with no codegen, (2) typed errors and dependency injection inside the server, (3) TanStack Query on both clients, (4) an OpenAPI spec, (5) learning curve for one maintainer new to Effect, (6) bundle size.

| Rank | Criterion | Effect v4 HttpApi verdict | Basis |
|---|---|---|---|
| 1 | End-to-end types, no codegen | **Meets** | `HttpApiClient` derives a typed client directly from the same `HttpApi` definition object used to build the server — no separate codegen step for the client direction. |
| 2 | Typed errors + DI inside the server | **Meets** | Per-endpoint `error` schemas plus `Context.Tag`/`Layer` DI are core, documented v4 mechanisms; "fixed client error... decoding" (July 2026 recap) confirms errors round-trip typed to the client too. |
| 3 | TanStack Query on both clients | **Not found in v4 sources** | No effect.website or GitHub source found pairs `HttpApiClient` with TanStack Query specifically; since the client is a plain async function per endpoint, wiring it as a TanStack Query `queryFn` is mechanically straightforward, but no primary source documents this combination for v4 — treat as an inference, not a confirmed fit. |
| 4 | OpenAPI spec | **Meets** | `OpenApi.fromApi` generates OpenAPI 3.1 directly from the same `HttpApi` definition — confirmed via direct fetch of the v4 API reference. |
| 5 | Learning curve, new to Effect | **Partial / risk** | Core HttpApi shape is small and declarative, but v4 is beta/RC with a moving API surface, and Workers-specific guidance is essentially absent from effect.website's own docs — see "Learning curve" section above. |
| 6 | Bundle size | **Favorable, secondary source** | InfoQ reports v4's minimal Effect+Stream+Schema bundle at ~20kB vs ~70kB for v3 — not independently re-verified against a first-party effect.website number in this pass. |

**Runtime-fit caveats that sit outside the ranking but bear directly on "can this be the whole shape of `apps/server` on Workers":**
- Durable-Object-SQLite `withTransaction` is broken today (open bugs #5987, #6006) — directly relevant given the map's chosen storage fallback is "a Durable Object per workspace with its SQLite storage."
- A cold-isolate, aborted-first-request wedge (#6319) is a production-availability risk on Workers specifically, filed against the same web-handler memoization pattern v4's httpapi/rpc builders still use.
- No confirmed compatibility between `@effect/vitest` and `@cloudflare/vitest-pool-workers` was found either way — needs a hands-on spike before committing to it for the "Tests are not optional" rule in issue #3's Notes.
