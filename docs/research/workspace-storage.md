# Workspace storage: Durable Object SQLite or D1 per tenant

Research for [#7](https://github.com/kryft-dev/prismark.tech/issues/7), part of the map in [#3](https://github.com/kryft-dev/prismark.tech/issues/3). All claims below are sourced from Cloudflare and Drizzle docs/source fetched during this research; each section cites its URL. Where a source did not say something, this doc says "not found" rather than filling the gap from memory.

## Summary

- A Durable Object per workspace, using `ctx.storage.sql`, is viable with Drizzle's `drizzle-orm/durable-sqlite` driver — schema, `migrate()`, and query builder all exist and are documented.
- DO SQLite storage: 10 GB per object cap, 30-day point-in-time recovery via bookmarks, storage billing starts January 2026 (row reads/writes + GB-month), and a soft throughput limit around 1,000 req/s per object.
- Routing is `idFromName(workspaceId)`: deterministic, same id always reaches the same object, no lookup table needed — this is strictly simpler than D1's per-tenant binding problem.
- WebSocket Hibernation (`state.acceptWebSocket`) coexists with SQLite storage on the same object; hibernation stops duration billing while connections stay open, so realtime is not precluded.
- `@cloudflare/vitest-pool-workers` exercises real Durable Objects (not mocks) via `runInDurableObject`, `listDurableObjectIds`, `runDurableObjectAlarm`, and `evictDurableObject` — including real SQLite storage.
- D1 is explicitly designed by Cloudflare for "per-user, per-tenant or per-entity databases" (10 GB cap each, up to 50,000 databases/account on Paid), which is direct primary-source backing for the named fallback.
- The blocker for D1-per-tenant is binding, not storage: Workers bindings are static, injected at deploy time from `wrangler.jsonc`/the Workers API — there is no documented runtime API to bind a new D1 database to a live Worker without a redeploy. A per-tenant D1 Worker must either redeploy on every signup or drop bindings for the D1 HTTP/REST API (`POST /accounts/{id}/d1/database/{db}/query`), which is a network call, not a binding read.
- The `import { env } from "cloudflare:workers"` rule (module-scope binding read, no per-request threading) holds for D1-per-tenant only if the binding set is static; it breaks the moment tenant creation needs a new binding without redeploying.
- The Durable Object shape has no such problem: `env.WORKSPACE_DO` is one static namespace binding read once at module scope, and `idFromName(workspaceId)` — computed per request from `ExecutionContext`/the request path, same as any per-request logic — selects the tenant. This fits the bindings rule cleanly; D1-per-tenant does not.
- Recommendation: **Durable Object per workspace with SQLite storage**, matching decision already recorded in issue #3's Notes; **shared D1 with `workspace_id`** stays the fallback exactly as named.
- What would make the prototype fail: Drizzle's DO SQLite driver missing DDL/relational-query support found live in code (a known 2024 GitHub gap, not yet confirmed resolved), a workspace needing to cross the documented per-object 10 GB or ~1,000 req/s ceiling, or `packages/db`'s workspace-scoping and sequence conventions (below) not translating cleanly onto per-object storage.

## SQLite storage API, size limits, pricing, and point-in-time recovery

The SQL API is exposed as `ctx.storage.sql`, available only on SQLite-backed Durable Objects. `sql.exec(query, ...bindings)` returns a `SqlStorageCursor`; multiple statements can be separated by `;` but bound parameters apply only to the last statement, and a cursor should be fully consumed synchronously before the next `await` to preserve snapshot isolation. Cursor methods: `.toArray()`, `.one()` (single row or throws), `.raw()` (array rows instead of objects), `.next()` (iterator protocol); cursor properties `.columnNames`, `.rowsRead`, `.rowsWritten` (used for billing). `storage.transactionSync(callback)` wraps synchronous work in a transaction and is exclusive to SQLite-backed objects; `storage.transaction(closure)` still exists but Cloudflare's docs note explicit transactions are "no longer necessary" for a sequence of writes with no intervening `await`, since those submit atomically. `storage.sql.databaseSize` is a read-only byte count of the object's SQLite database.
Source: https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/ and https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/

Limits (Durable Objects, SQLite backend): 10 GB max per object; 5 GB per account on the Free plan, unlimited (subject to total account storage) on Paid; max 100 columns per table; max string/BLOB/row size 2 MB; max SQL statement length 100 KB; combined key/value size 2 MB; WebSocket messages up to 32 MiB received; up to 500 DO classes (Paid) / 100 (Free); soft limit ~1,000 requests/second per individual object; CPU time 30s default, configurable up to 5 minutes; wall time unbounded while the caller stays connected. When a SQLite-backed object hits its cap, writes fail with `SQLITE_FULL` while reads and deletes keep working.
Source: https://developers.cloudflare.com/durable-objects/platform/limits/

Pricing (Workers Paid): compute is 1M requests/month included + $0.15/million (covers HTTP requests, RPC sessions, WebSocket messages, alarm invocations), and 400,000 GB-s/month duration included + $12.50/million GB-s (128 MB allocated per object regardless of use); storage billing for the SQLite backend activates January 2026 — row reads: 25 billion/month included + $0.001/million rows; row writes: 50 million/month included + $1.00/million rows; stored data: 5 GB-month included + $0.20/GB-month; key-value `get`/`put`/`delete`/`list` are billed as row reads/writes against hidden SQLite tables. Free plan (daily): 100,000 requests, 13,000 GB-s duration, 5M row reads, 100,000 row writes, 5 GB total stored data; Free plan supports only SQLite-backed objects (no legacy KV backend).
Source: https://developers.cloudflare.com/durable-objects/platform/pricing/

Point-in-time recovery: SQLite-backed Durable Objects can be restored to any point in the past 30 days using bookmarks — opaque, lexically-comparable strings. `getCurrentBookmark()` returns a `Promise<string>` for the present moment; `getBookmarkForTime(timestamp)` resolves a bookmark for a timestamp within the last 30 days; `onNextSessionRestoreBookmark(bookmark)` schedules a restore on the object's next start and itself returns a bookmark representing the pre-recovery state (so a bad restore is itself undoable). PITR covers both SQL data and the object's key-value data. Restore is not available in local development. Extensions supported inside DO SQLite: FTS5 (full-text search), JSON functions, math functions; virtual tables created by extensions count toward billing.
Source: https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/

## Drizzle's Durable Object SQLite driver: schema, migrations, query API, gaps

Driver: `import { drizzle, DrizzleSqliteDODatabase } from 'drizzle-orm/durable-sqlite'`. In the Durable Object constructor, `this.db = drizzle(this.storage, { logger: false })` — the driver takes the object's `DurableObjectStorage` directly (not the raw `ctx.storage.sql`). Migrations are generated by `drizzle-kit` configured with `dialect: 'sqlite'`, `driver: 'durable-sqlite'`, and run at object start via `migrate` imported from `drizzle-orm/durable-sqlite/migrator`, wrapped in `ctx.blockConcurrencyWhile(async () => { await this._migrate() })` so no query is served until migrations finish. `wrangler.toml`/`wrangler.jsonc` needs a `[[rules]]` entry (`type = "Text", globs = ["**/*.sql"]`) to bundle the generated `.sql` migration files, plus the standard `[[durable_objects.bindings]]` and a `new_sqlite_classes` migration tag for the class. Query API is the normal Drizzle query builder once `this.db` exists. Cloudflare's own guidance layered on top: batch DB interactions inside a single Durable Object call, since each external call to the object incurs its own round trip.
Source: https://orm.drizzle.team/docs/sqlite/connect-cloudflare-do

Gap found in Drizzle's own tracker (drizzle-team/drizzle-orm GitHub discussion #3029): the original ask was for the driver to give the DO SQLite API type-safety, and a contributor flagged there was, at the time, "no DDL solution to create database tables and indices outside of using the Drizzle Kit CLI or vanilla SQL" — i.e. the driver leans on `drizzle-kit` (an offline codegen/CLI step) for schema DDL rather than a fully in-driver programmatic path. A PR (#3053) addressing this was reported "not really ready yet" as of the discussion. This repo's `packages/db` already generates a Drizzle schema and migrations from a markdown-first spec, so this gap is consistent with the existing workflow (drizzle-kit generates, the object applies at start) rather than a blocker — but it should be re-verified against the current driver/PR state before committing to the shape, since "not found" is the honest answer for whether it has since been closed.
Source: https://github.com/drizzle-team/drizzle-orm/discussions/3029

## Routing: one object id per workspace, and the cost of crossing into the object

`env.WORKSPACE_DO.idFromName(workspaceId)` (or `idFromString`) produces a deterministic id: "the same input always produces the same Durable Object ID, ensuring requests for the same logical entity always reach the same instance." Creating a stub does not instantiate the object; it only spins up (or wakes) on first method/fetch call. This means: no lookup table, no directory service, no extra network hop to resolve "which shard has workspace X" — the id computation is pure and can run inside the Worker's handler, then `env.WORKSPACE_DO.get(id)` gets the stub and the request crosses into the object. Cloudflare's own recommended pattern for multi-tenant, heavy-read scenarios is explicitly "one DO per tenant" rather than a global coordinator, warning against "a single 'global' Durable Object that handles all requests" as an unscalable bottleneck. Per-object throughput is roughly 500–1,000 req/s depending on operation complexity (simple pass-through near 1,000/s, complex operations 200–500/s); each instance executes single-threaded, though `fetch()`-style async work can interleave via input/output gates that protect storage consistency. Reads should use SQL indexes on queried columns and can cache in memory to cut cross-object latency.
Source: https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/

Every request that touches workspace data crosses into its object — this is the shape's cost, not a hidden one: each such call is its own billed request (a single RPC session, or a single HTTP request to the stub); a WebSocket connection is one billable request to open, then incoming messages count at a 20:1 ratio toward compute billing (100 incoming messages ≈ 5 billed requests), and outgoing messages plus WebSocket protocol pings are not charged.
Source: https://developers.cloudflare.com/durable-objects/platform/pricing/

## WebSocket hibernation on the same object

`state.acceptWebSocket()` (as opposed to the plain `ws.accept()`) is what makes a connection hibernation-eligible: when the object receives no events for a short period it is evicted from memory (in-memory state resets), and on the next event (message, alarm, etc.) the constructor reruns and the object reinitializes while connected clients stay attached to Cloudflare's network. Per-connection state can be preserved across hibernation with `serializeAttachment(value)` (16,384-byte cap) / `deserializeAttachment()`; larger state should live in the Storage API, referenced by key from an attachment. Billing: "Billable Duration (GB-s) charges do not accrue during hibernation," and `state.setWebSocketAutoResponse()` responses also do not incur wall-clock charges. The docs fetched for this research do not explicitly state whether a hibernating object can concurrently serve SQL queries from its own SQLite storage while hibernated — not found in the pages checked — but nothing in the hibernation docs or the SQLite storage docs describes the two features as mutually exclusive, and the constructor-rerun-on-wake model is exactly the model the migration pattern above (`blockConcurrencyWhile` in the constructor) already assumes, so realtime is not precluded by the storage choice.
Source: https://developers.cloudflare.com/durable-objects/best-practices/websockets/

## Testing inside Cloudflare's Vitest pool with real objects

`@cloudflare/vitest-pool-workers` exercises real Durable Objects, not mocks. Its `cloudflare:test` module exports: `runInDurableObject(stub, callback)`, which temporarily replaces the object's `fetch()` handler with `callback`, sends it a request, and returns the result — letting a test call or spy on the object's actual methods and read its persisted (real SQLite) storage directly; `listDurableObjectIds(namespace)`, which lists ids created within a namespace, scoped per test file so objects from other test files aren't visible; `runDurableObjectAlarm(stub)`, which immediately runs and clears any scheduled alarm, returning whether one ran; and `evictDurableObject(stub)` / `evictAllDurableObjects()`, which tear down an instance's in-memory state while preserving durable storage, so a test can exercise the production eviction/reinitialize lifecycle (including resuming hibernated WebSockets or re-running constructor migrations) deliberately.
Source: https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/

## Failure modes

- **Object stuck.** Not found in the docs fetched: no explicit "durable object stuck" failure mode or recovery procedure surfaced. The closest documented lever is PITR (`onNextSessionRestoreBookmark`) to roll a corrupted object's SQLite state back to a known-good bookmark within 30 days, and `evictDurableObject`-style forced eviction (available as a test helper; not confirmed as a production operator tool in the pages checked) to force a constructor rerun.
- **Migration failed mid-way.** The documented pattern runs `migrate()` inside `ctx.blockConcurrencyWhile()` in the constructor, so the object does not begin serving requests until migration completes; a failure there throws inside `blockConcurrencyWhile` and (per the general SQLite storage/transaction docs) rolls back rather than committing a partial schema, since `transactionSync` failures roll back on exception — but no page fetched for this research specifically walks through a mid-migration crash-and-recover scenario for the DO driver. That is a real open question to prototype rather than something already answered by docs.
- **Cross-workspace queries.** `packages/db/README.md`'s domain model has each root table carry its own `workspace_id`, and the map (issue #3) confirms the inbox spans one workspace ("the inbox spans one workspace, so probably none"). With one Durable Object per workspace, a cross-workspace query is not just discouraged, it is structurally impossible without querying multiple objects and merging in the Worker — there is no shared connection pool to accidentally leak across tenants the way a single shared D1 with `workspace_id` filtering could (a missing `WHERE workspace_id = ?` is a live SQL-injection-adjacent risk under the fallback shape; it cannot happen under the DO shape because there is no other workspace's rows reachable from a given object at all).

## D1 per tenant

D1 is explicitly positioned by Cloudflare for this exact pattern: "D1 is designed for horizontal scale out across multiple, smaller (10 GB) databases, such as per-user, per-tenant or per-entity databases." Per-account limits (Workers Paid): 50,000 databases (10 on Free), 1 TB total storage (5 GB Free), both "expandable by request." Per-database limits: 10 GB max size (hard cap, not increasable even on request), 1,000 queries per invocation (50 Free), up to 6 simultaneous connections per Worker invocation, 30s max query duration, 2 MB max row/string size, 100 KB max SQL statement length. Throughput is bound by query duration since each database processes sequentially: ~1,000 queries/sec at 1ms/query, ~10/sec at 100ms/query. Bulk `UPDATE`/`DELETE` must be chunked (e.g. 1,000 rows at a time) to stay under limits.
Source: https://developers.cloudflare.com/d1/platform/limits/

**Creating a database on sign-up, through the API.** `POST https://api.cloudflare.com/client/v4/accounts/{account_id}/d1/database` with body `{ "name": ... }` (optional `jurisdiction`, `primary_location_hint`, `read_replication.mode`), authenticated with a "D1 Write"-scoped API token, returns the database's `uuid`, `name`, `created_at`, etc. This is a Cloudflare account-management API call, not a Worker binding — it can run from a sign-up handler to provision a tenant's D1 database at account level.
Source: https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/create/

**How it is bound at request time.** This is the actual friction point, and it is the reason the shared-D1 fallback exists. Workers bindings — D1 included — are declared statically in `wrangler.jsonc`/`wrangler.toml` and injected at deploy time; per this repo's own convention (`docs/agents/cloudflare.md`), the Worker reads them once at module scope via `import { env } from "cloudflare:workers"` and builds `drizzle(env.DB, { schema })` off that. There is no documented Cloudflare runtime API to attach a newly created D1 database as a binding on an already-deployed Worker without redeploying it (updating the script via the Workers API with a new binding list, or via `wrangler deploy`). A Worker can statically list up to ~5,000 D1 bindings (`Approximately 5,000` D1 databases can bind to a single script, per the limits page), so a small/medium fleet of tenant databases could in principle all be bound to the same Worker script and selected by name at request time (`env[`DB_${tenantId}`]`) — but every new tenant still requires appending a binding and redeploying, which conflicts with "sign up creates a tenant instantly." The documented alternative that avoids a binding entirely is the D1 HTTP/REST query API — `POST /accounts/{account_id}/d1/database/{database_id}/query` with `{ sql, params }` or `{ batch: [...] }`, authenticated the same way as database creation — which lets a Worker (or any client) run SQL against a tenant's D1 database purely by `database_id`, with no static binding and no redeploy, at the cost of an authenticated network call per query instead of a binding call, and outside the `env`-at-module-scope pattern entirely (it is a `fetch()` to Cloudflare's API, evaluated per request with the tenant's `database_id`, not a binding read).
Source: https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/create/ , https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/ , https://developers.cloudflare.com/d1/platform/limits/

Workers for Platforms' dynamic dispatch was checked as a possible way around static bindings: user Workers deployed to a dispatch namespace can be given bindings to D1/R2/KV, and Cloudflare's May 2026 "Dynamic Workflows" changelog describes per-tenant dispatchable D1/D1-like bindings as a stated direction ("every binding Workers currently exposes is heading for a dynamic counterpart... dispatchable per tenant, per agent, per request, at zero idle cost"), but the specific mechanics of binding a D1 database to a dynamically-dispatched Worker at request time were not found in the pages fetched, and this repo is not using Workers for Platforms — this project runs one Worker per app (issue #3: "`apps/server` is its own Worker at api.prismark.tech"), not a multi-tenant Worker-per-tenant dispatch model, so this path is out of scope for the fallback shape as currently decided.
Source: https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/how-workers-for-platforms-works/ , https://www.infoq.com/news/2026/05/cloudflare-dynamic-workflows/ , https://developers.cloudflare.com/changelog/post/2026-05-01-dynamic-workflows/ — the last two are third-party/changelog summaries of a direction, not confirmation of a shipped runtime D1-binding API; treat as "not found" for anything beyond direction.

**What a self-hoster with one workspace gains or loses.** With D1-per-tenant, a self-hoster running exactly one workspace still needs the account-level D1 creation flow, a binding for that one database (static and fine — one tenant, one redeploy at setup, no ongoing churn), and gets the full 10 GB / per-database limits above to themselves. They lose nothing structurally versus the shared-D1 fallback for their single tenant, but they inherit the same "create D1 database via account API + bind + redeploy" bootstrap step that a hosted multi-tenant deployment would have to repeat per signup — for one workspace this cost is paid once, so D1-per-tenant is actually simplest for the self-host case specifically. For the Durable Object shape, a self-hoster gets the same simplicity: one `WORKSPACE_DO` namespace binding (static, declared once), one workspace id, no created-database step or account-level API call needed at all — Durable Object namespaces don't need per-tenant account provisioning the way D1 databases do.

## What changes in `packages/db` conventions under each

Per `packages/db/README.md`, current conventions: ULID `id text` per table with a per-workspace integer sequence for human-facing numbers (`task.number`, `invoice.number`, `deal.number`) stored on the workspace row; timestamps as `integer` unix milliseconds; booleans as `integer` 0/1; `workspace_id` present on root tables only, with children reaching workspace through their parent; enums as `text`; `created_at`/`updated_at` convention; soft deletes via `deleted_at`. Issue #3's Notes record that `packages/db` "dissolves into `apps/server/src/db`" once code lands — the file conventions themselves are what's being evaluated here.

| | Durable Object per workspace | Shared D1 + `workspace_id` (fallback) | D1 per tenant |
|---|---|---|---|
| **ULIDs** | Unchanged — still `id text` ULID. Per-workspace sequence gets simpler: it's the only workspace in this database, so the "per-workspace" qualifier on the sequence is now structural, not a filtered query. | Unchanged; sequence increment must stay scoped by a `WHERE workspace_id = ?`. | Unchanged; sequence is local to the tenant's DB, same simplification as DO. |
| **Integer timestamps / no booleans** | Unchanged; DO SQLite is still SQLite with the same four affinities (`text`, `integer`, `real`, `blob`), so every existing rule in the README holds verbatim. | Unchanged. | Unchanged; D1 is also SQLite. |
| **`workspace_id` on root tables** | Becomes redundant, not wrong: every row in the object already belongs to one workspace. Keeping the column costs nothing and preserves a single shared Drizzle schema across shapes, but it stops doing any filtering work — every query is implicitly workspace-scoped by which object answered it. | Unchanged and load-bearing: every root-table query still needs `WHERE workspace_id = ?`, and a missing filter is a cross-tenant data leak. This is the shape where the column's correctness matters most. | Same simplification as DO — redundant but harmless, since the tenant boundary is the database file, not the column. |
| **Migrations** | Driven by `drizzle-kit` (dialect `sqlite`, driver `durable-sqlite`) generating `.sql` files bundled via a wrangler `[[rules]]` text-glob entry, applied per-object inside the constructor under `ctx.blockConcurrencyWhile`. Every workspace's object migrates independently, on its own first-wake-after-deploy — no single migration run touches every tenant at once. | Standard `drizzle-orm/d1` + `drizzle-kit` migrations against one database, run once for all tenants. | Same `drizzle-kit`/`d1` migration tooling as shared D1, but must run once per tenant database — an N-database migration fan-out rather than one run. |
| **Connection/binding code** | One static `env.WORKSPACE_DO` namespace binding read at module scope (fits `docs/agents/cloudflare.md` exactly); `idFromName(workspaceId)` computed per request selects the tenant, no new binding ever needed. | One static `env.DB` binding read at module scope (fits the rule exactly, already the pattern in `packages/db/README.md`'s target state). | Breaks the static-binding-at-module-scope model at fleet scale: either redeploy per new tenant to add a binding, or move off bindings entirely to the D1 HTTP API (a per-request authenticated `fetch()`, evaluated with the tenant's `database_id`, not a module-scope `env` read) — a bigger architectural change than the other two shapes require. |

## Open questions

- Whether the Drizzle DO SQLite driver's DDL gap (drizzle-team/drizzle-orm discussion #3029, PR #3053 "not really ready yet" as of the discussion) has since closed — not found in the pages fetched; needs a direct look at the current driver source/changelog before the prototype starts, not this doc.
- Whether a hibernating Durable Object can serve `ctx.storage.sql` queries concurrently with a hibernated WebSocket session on the same object — not found in the docs fetched; likely yes given the shared constructor/wake model, but not explicitly stated anywhere checked.
- What "object stuck" concretely means operationally for a SQLite-backed DO in production (beyond PITR rollback and forced eviction) — not found in the docs fetched.
- Exact behavior of a crash mid-`migrate()` inside `blockConcurrencyWhile` — rollback semantics are implied by the general SQLite transaction docs but not walked through for this specific driver/pattern combination.
- The real mechanics (if any exist today, outside Workers for Platforms) for provisioning a new D1 binding onto a live Worker without a redeploy — the WebSearch/WebFetch results found only the D1 HTTP API and Workers-API-triggered redeploy as concrete answers; if a newer mechanism exists it wasn't surfaced.
